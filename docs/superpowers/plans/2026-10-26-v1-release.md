# Version 1.0.0 release implementation plan

> **For agentic workers:** Execute inline with superpowers:executing-plans. The user explicitly authorized preparing, merging and publishing this release.

**Goal:** Merge the release branch to main as v1.0.0 and publish a ready-to-run GHCR image, with a clone-free Portainer deployment guide.

**Architecture:** A main-only workflow runs the existing correctness gate, calculates a semantic version from reachable release tags and Conventional Commits, builds/publishes a multi-platform image, then creates the matching GitHub release with deployment assets. Initial release is exactly 1.0.0; later breaking changes bump major, features bump minor, and all other merged changes bump patch. The tag and image identify the same tested commit. A manual main-branch run supports recovery; an already published commit is skipped.

**Tech Stack:** GitHub Actions, Python standard library, Docker Buildx, GHCR, Docker Compose, Django.

**Spec:** User request dated 2026-10-26; existing application design and proxy contract remain applicable.

## Global constraints

- First release: v1.0.0, image ghcr.io/bcl1713/backstory:1.0.0 (also v1.0.0, 1.0, 1, latest).
- Publish linux/amd64 and linux/arm64; no npm or Python package publication.
- Image publication precedes the public GitHub release; failed correctness blocks publication.
- Portainer Docker Standalone uses compose.portainer.yaml without checkout or build context.
- Reuse the existing Cloudflare connector or Nginx Proxy Manager; retain exact hosts, HTTPS cookies, CSRF origins and trusted actual proxy peers.
- Interactive account passwords only; persistent private data outside the wiki; no live storage or proxy changes.

## Review focus

- Bootstrap must remain 1.0.0 despite historical breaking commits.
- A failed or repeated release must not invent a new version for the same commit.
- Major/minor detection must handle scopes, bang notation and breaking footers.
- A tag on an unrelated branch must not affect main's version.
- Portainer variables must reach the actual mounts and process, preserving non-root ownership and proxy controls.
